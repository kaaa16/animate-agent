# 项目期望总结

## 1. 项目愿景

Animate Agent 的目标是把枯燥、密集、难读的技术文档变成简单易懂、有趣、可互动的教学网页。产品定位应从普通阅读器升级为 **Interactive Knowledge Movie（交互式知识电影）**。

用户给 Agent 一份官方文档或手册，Agent 应该输出：

- 文档核心逻辑的结构化理解。
- 面向初学者的教学分镜。
- 具象的动画演示。
- 可调整参数的互动 demo。
- 辅助理解的文字说明，而不是大段摘要。

典型体验应该是：

- 上传 ROS 手册。
- AI 分析章节。
- 自动生成知识图谱。
- 用户进入第一页。
- 滚轮推进镜头。
- Publisher、Topic、Subscriber 等对象依次出现。
- Topic 消息在节点之间飞行。
- 点击 Topic 弹出源码。
- 点击源码后，对应 ROS 节点高亮。
- 点击节点播放控制动画。
- 拖动机器人并实时模拟状态变化。

## 2. 体验目标

- 用户第一眼能看出文档在讲什么。
- 每个核心概念都有对应的可见对象。
- 每个关键因果关系都有动画变化。
- 用户可以通过拖动、滑杆、播放、暂停、单步推进来验证理解。
- 页面风格偏赛博朋克教学控制台：清晰、精密、有科技感，但不能牺牲可读性。
- 体验更像游戏 + 交互课件，而不是阅读器。

## 3. 小车避障示例的目标质量

如果文档讲小车避障，页面不能只写“雷达检测障碍后转向”。它至少要展示：

- 小车本体。
- 车头方向。
- 激光雷达扇形扫描。
- 多条测距射线。
- 障碍物。
- 安全距离阈值。
- 最近命中点。
- 控制器决策。
- 转向绕行轨迹。

互动上至少支持：

- 调整车速。
- 调整雷达半径。
- 调整安全距离。
- 调整障碍密度。
- 拖动障碍物。
- 播放、暂停、重置、单步讲解。

## 4. Agent 工作流期望

推荐工作流如下：

1. 文档解析
   - 将 PDF、网页、Markdown、纯文本转成结构化章节块。

2. 内容理解
   - 提取对象、参数、流程、状态、条件、异常处理。

3. 教学设计
   - 将技术内容拆成多个“教学镜头”。
   - 每个镜头说明画面对象、动作、重点和用户交互点。
   - 对 ROS、API、机器人、状态机等常见领域，优先匹配已有交互模板。

4. 动画规格生成
   - 生成受控 JSON spec。
   - 只允许使用对象库和模板库中的动画元素。
   - 输出镜头、对象、运动、点击行为、源码关联和图谱关系。

5. 前端渲染
   - Canvas/SVG/Three.js 渲染 spec。
   - 参数控件实时影响画面结果。

6. 质量检查
   - 检查是否只是文字堆叠。
   - 检查关键对象是否可见。
   - 检查交互是否真实改变动画。
   - 检查新手是否能通过画面理解核心逻辑。

## 5. 工程原则

- Python 后端负责理解、编排、生成 spec。
- 前端负责渲染和交互，不直接信任模型生成代码。
- 动画对象和互动控件必须复用，避免重复造轮子。
- 每种常见文档类型沉淀一个模板库。
- 所有模型输出都要经过 schema 校验。
- 每个模板都要有最小单元测试。

## 6. 当前阶段范围

当前阶段不是直接做完整商业产品，而是先建立正确的工程地基：

- 规范 Python 项目结构。
- 归档已有静态 demo。
- 建立动画元素和互动元素的对象模型。
- 写清技术栈、产品目标、质量标准。
- 为后续接入真实 Agent 和渲染器打基础。
- 在当前静态 demo 中先实现一个最小 ROS 交互课件，验证“知识电影”的交互方向。

## 7. 最小 ROS 交互课件标准

- 画面包含 Publisher、Topic、Subscriber、消息包和机器人。
- 消息包应沿 Topic 通道飞行，并在接收后改变颜色。
- 点击 Topic 时，页面展示对应源码片段。
- 点击源码时，画面高亮相关 ROS 节点。
- 机器人可拖动，拖动后模拟状态应实时变化。
- 滚动或单步操作能推进教学镜头。
