# Storyboard 里程碑：从 LessonIR 到可直接看见的画面

date: 2026-09-13
status: active

## 里程碑目标

打通 `LessonIR → StoryboardIR → RenderSpec → 画面` 这条链。在此之前 LessonIR 没有任何消费方，
`frontend/demo/` 的 canvas 渲染器是**不可达的死代码**（`index.html` 把标记整段注释掉且不加载 `app.js`）。
断点在中间那一环：Storyboard。

## 质量基线

**用户明确要求：动画效果与质量尽量与「小车避障」那份动画对齐。**
即 `animation/templates.py` 的 `build_robot_obstacle_avoidance_scene()` 与
`frontend/demo/app.js` 里 `drawRobot()` 画出来的东西。它是本阶段的**及格线**，不是参考。

这条基线有可机检的含义：**词表必须能表达那份场景画出的每一个量**。
对照后发现的缺口（已修）：

| 基线里的写法 | 原词表 | 处理 |
|---|---|---|
| `lidar.radius`（滑杆「雷达半径」） | `emitter.reach` | 改名 `radius`，与基线同名 |
| `scene.safe_distance`（滑杆「安全距离」） | 不存在 | 加入 `proximity_gate.reads` → 可作控件目标 |
| `reset` 按钮：`target_property="scene"` + `action` | 校验台强制要求 `<obj>.<prop>` | 按钮改按 `action` 校验（`BUTTON_ACTIONS`） |

基线的三个滑杆（车速 / 雷达半径 / 安全距离）现在全部可表达。
**注意 `lidar.radius` 与 `scene.safe_distance` 是两个不同的量**——探测距离 vs 判定阈值——
不能合成一个 prop，否则「调雷达半径」和「调安全距离」会变成同一个动作。

## 实施顺序（2026-09-13 调整）

原计划先落校验台再落生成器，**已改为先产出 StoryboardIR**：

| 序 | 内容 | 完成判据 |
|---|---|---|
| **S1** | `storyboard/{models,validation,prompts,agent,service}.py`、`rendering/registry.py`、`config.py` + YAML、`cli.py --storyboard` | 一份真文档跑出**真的 StoryboardIR JSON**，过校验台，落到 `data/generated/` |
| **S2** | `rendering/{models,layout,legacy,service}.py`、registry 的 T2 字形数据、`assets/glyphs/` | 同一份 StoryboardIR → 确定性 RenderSpec |
| **S3** | `frontend/player/*`、`api.py` 挂载与端点 | 浏览器里看见画面，滑杆真的改变结果 |
| **S4** | 对照工具、手写 fixture、本文档补齐 | 三方并排对比有结论 |

**为什么改序**：校验台只有在有东西可校验时才有意义；而先出真输出，下游的布局与播放器才有**真实**的
StoryboardIR 做靶子，而不是我自己猜的 fixture。原计划把手写 fixture 放在最前，等于用猜的东西约束真东西。

**S1 的内部依赖**：`agent.py` 的重试循环要吃校验台的报错，所以 registry + validation 必须在 S1 内，
但它们不必先于 models 完成——这是同一切片内部的三步，不是三个切片。

## M1–M4：把「生成动画」拆成四个能跑的切片（2026-09-13 追加）

S1–S4 是**交付**顺序；下面是把 S2/S3 内部再拆细后的**搭建**顺序。理由是一条：
**`legacy` 必须走在 `layout` 前面。** 布局算法是拿坐标的，而坐标对不对，只有一张**已经画对的画面**
能判断。`legacy.py` 不需要任何布局算法——它只是把基线那份手写 `Scene` 翻译成 `RenderSpec`——
于是它免费给出两样东西：一张基准画面，和一次对 `RenderSpec` 契约的**真实性检验**。
反过来先写 `layout.py`，就只能对着自己的想象调槽位。

| 切片 | 内容 | 判据 | 状态 |
|---|---|---|---|
| **M1 看见第一帧** | `rendering/{models,legacy}.py` + `frontend/player/` | `--render-template robot_obstacle_avoidance` → 浏览器里出现小车避障画面，拖滑杆结果真的变 | **已完成（2026-09-13 浏览器验收通过，遗留三条见下文）** |
| **M2 学会自己摆** | `rendering/layout.py`，先只做 `lane` | 手写 sample → RenderSpec → 与 M1 画面同义、并排可对照 | **已完成（2026-09-13）**，见下节 |
| **M3 补齐词汇** | 其余 4 个预设 + 剩余 T1 图元 + T2 字形 | 抛体 sample 也画得出（v₀ 分解、坐标轴、射程标注） | **进行中**：`chain`/`generic` 已完成（2026-09-13），余 `hub`/`field` + 几何图元 + 字形 |
| **M4 全链路** | 真文档 → lesson → storyboard → layout → 画面 | 一条命令出画面 | 未开始 |

**M1 为什么单独切出来**：计划书风险 5 说「播放器是最大单项工作量，不要按薄序列化层排期」。
把它和布局算法塞进同一个提交，等于两个大件同时开工、同时调试——出问题时**分不清是布局摆错了
还是播放器画错了**。M1 让播放器面对一个**已知正确的输入**（基线翻译），于是它的正确性可以脱离
布局独立判定。

### 播放器的三条硬规则，以及它们的机检形式

| 规则 | 机检 |
|---|---|
| 前端绝不执行模型生成的代码（D4） | `test_the_player_never_executes_spec_text`：**剥掉注释后** grep `eval(`／`new Function(`／`innerHTML` |
| 播放期 0 次 LLM，也不该有别的网络请求 | `test_the_player_fetches_the_spec_exactly_once`：全部源码里 `fetch(` 恰好 1 处 |
| registry 与播放器不漂移 | `test_the_player_accounts_for_every_registered_primitive`：`DRAWERS` ∪ `PENDING_KINDS` == 13 个 T1 图元 |

第一行那个「剥掉注释」是有来由的：第一版检查让**我自己解释这条规则的注释**绊倒了测试。
一条禁止提及某物的检查，也禁止了解释它为什么被禁。

### 怎么验收（浏览器检查与 pytest 分开，按 Standing Correction）

```
.\.venv\Scripts\python.exe -m http.server 8000      # 在仓库根目录
```

打开 `http://127.0.0.1:8000/frontend/player/index.html`（默认是 `lane` 基线画面；
加 `?spec=/data/generated/render-ros_pub_sub.json` 看 ROS 链路）。确认三件事：

1. **画面出现**：小车（带朝向三角）、扇形雷达射线、虚线安全圈、两个八角障碍、车道网格。
2. **节拍可单步**：点「▶ 下一拍」或按 `→`，高亮跟着换到对应的对象。
3. **滑杆真的改结果**：拖「车速 / 雷达半径 / 安全距离」，**画面随之改变**——不是只有数字变。
   这是项目规则「交互参数必须改变结果」在浏览器里的那一半。

**M2 的并排对照**用同一个页面的两个标签页——同一个播放器、同一个 stage，
所以两边的差别只可能出在布局那一层（左手是翻译，右手是布局）：

| 看的是 | spec | 怎么来的 |
|---|---|---|
| 基线 | `?spec=/data/generated/render-robot_obstacle_avoidance.json` | `--render-template`，翻译冻结的 `templates.py` |
| 布局 | `?spec=/data/generated/render-sample-robot_obstacle_avoidance.json` | `--render-sample`，`layout.py` 摆手写的 sample |

`node tools/player_smoke.mjs <spec.json>` 是**无头冒烟检查**：每个元素在每一拍各画一遍，
经由一个记录调用的假 canvas 上下文。它抓拼写错误、缺失方法、以及**什么都没画的元素**；
它抓不住「车画得不好看」——那仍然是人眼检查。**两者故意不混为一谈。**

## 决策记录

> 这一节记的是**当时的判断和它的失败症状**。后续在这里翻不到原因时，说明问题出在别处。
> 判据是「可观测症状」——故意写成人能撞见的样子，好让它可被搜索到。

### D1 — 字形的「结构」属性归资产，「主题」属性归主题层

**决定**：

| 字段 | 归属 | 理由 |
|---|---|---|
| `d`、`mode: "stroke" \| "fill"`、`fillRule` | **字形资产**，必填 | 这是**几何的性质**，不是审美选择 |
| `strokeWidth` | 字形里作**可选默认值**，主题可覆盖 | 介于二者之间 |
| 颜色（stroke / fill 色值） | **主题层**，绝不进资产 | 这是审美选择，且要能随状态变 |

**为什么**：`Path2D` **只带几何不带样式**。Tabler / Lucide / Heroicons-outline 是**只有描边**的图标，
用 `ctx.fill()` 画出来是**一坨实心黑块**；Material Symbols 反过来是**只有填充**的。
所以 `mode` 必须随几何走——换了绘制方式就是错的，这不是主题能补救的。
反面是颜色：`body` 有 `danger` / `visible` 属性，而 `proximity_gate` 行为会在**播放期**把 `danger` 翻成真。
颜色若冻在资产里，**危险态画不到字形上**。

**违反后的可观测症状**：
- 漏 `mode` 或 `mode` 传错 → **图标变成实心黑块**（描边图标被 `fill`），或只剩轮廓（填充图标被 `stroke`）。
- 漏 `fillRule: "evenodd"` → **轮毂、散热孔这类子路径挖的洞被填实**（`Path2D` 默认 `nonzero`）。
- 颜色写进资产 → 危险/失效状态下**字形不变色**，而同一场景里的 `body` 主体变了色，两者对不上。

**护栏**：① 字形 schema 把这三个字段设为必填，加载时硬校验；
② 每个字形各渲一次的视觉快照测试——这是唯一能抓住「不报错但画错」的手段；
③ 构建期归一化脚本是唯一的产出路径，`assets/glyphs/*.json` 里的 `d` **不得手改**
（手改的字形不可再生成，schema 一变就变成迁移负担）。

### D2 — `parts` 扁平，一层，不递归

**决定**：字形的 `parts` 是 `名字 → 部件` 的**一层映射**，部件不能再是组。

**为什么**：递归意味着 JS 加载器要写树遍历、世界变换要逐层叠、`anchor` 要相对父级解析。
四个目标域（避障 / ROS / API / 抛体）都用不到。`parts` 存在的**唯一**理由是可分别变换与着色
——车和轮子合成一条 path，**轮子就转不起来**——这个理由一层就够。

**违反后的可观测症状**：出现「子部件的旋转轴跟着父部件漂移」这类 bug；
或加载器里长出递归代码，而没有任何字形真的用到它。

**护栏**：schema 层直接拒绝嵌套（部件的值是部件对象，不是部件列表）。

### D3 — 语义给模型，布局给代码

**决定**：模型输出对象、角色、关系、节拍顺序、哪些参数做成控件；**坐标、像素尺寸、颜色、层叠、缓动一律由代码算**。
`StoryboardIR` 里**没有 x/y**。

**为什么**：模型在坐标上不可靠，且不可复现；而「一份输入 → 同一份画面」是能对照评测的前提。
`animation/elements.py` 里的 `position` 字段因此在契约中被丢弃。

**违反后的可观测症状**：同一个 LessonIR 两次生成出**布局不同**的画面；
或模型给出的坐标越界/重叠，且没有任何一层拦得住。

**护栏**：`StoryboardIR` 模型里根本没有坐标字段（`extra="forbid"` 会拒绝模型硬塞进来的坐标）；
布局层是纯函数，有确定性 golden 测试。

### D4 — 前端绝不执行模型生成的代码

**决定**：播放器只消费受控 JSON spec。公式**不是文本，是几何**——构建期渲成 path 走 `Path2D`。
禁止 `eval` / `new Function` / `innerHTML`。

**来源**：`.agents/memory/project-overview.md` 的 Standing Corrections，有约束力。

**违反后的可观测症状**：播放器源码里出现 `eval(` / `new Function` / `innerHTML` 赋值。

**护栏**：验收时 grep 播放器源码；spec 文本一律 `textContent`（**不学 `frontend/demo/app.js:210` 的 `innerHTML` 用法**）。

### D5 — schema 的每一条约束都必须在 prompt 里出现，且由 schema 生成

**决定**：`StoryboardIR` 的字段约束（长度、正则）由 `prompts.render_field_constraints()`
从 pydantic 模型本身渲染进 system prompt，**不手抄**。

**为什么**：prompt 主要靠**例子**教学。例子覆盖不到的约束，模型不知道它存在——而它一定会踩。
第一次真跑（8 个课程场景 → 5 个分镜场景）就是这么死的：

```
scenes.0.steps.0.description：String should have at least 20 characters
scenes.3.objects.5.id：String should not match pattern '^[a-z][a-z0-9_-]*$'
```

33 处 schema 不符里，31 处是前者，2 处是后者。**两条约束都真实存在于 schema 里，
两条都没写进 prompt。** 模型没法遵守它没被告知的东西。

**这条不是猜的——基线自己就过不了 `description >= 20`：**

| 基线（`build_robot_obstacle_avoidance_scene`）的节拍文案 | 字数 |
|---|---|
| 雷达向前方扇形区域发射多条测距射线。 | 19 |
| 最近回波被标记为危险候选点。 | 14 |
| 最近距离低于安全距离时，控制器进入避障状态。 | 22 |
| 控制器比较左右空旷程度，选择更安全的一侧。 | 21 |

4 条里 2 条低于 20。**我把一个自己拍的数字写进了 schema，再用它去否掉它本来要学的那种写法。**
下限已改成 12（基线最短 14 再留 2 字余量），由
`test_the_quality_baseline_satisfies_the_step_schema` 看住——它把基线的原文直接喂给 `StoryboardStep`，
所以下限再也抬不过基线。

**违反后的可观测症状**：模型因为一条它无从知道的规则被反复打回，重试三次后报
「多次重试仍无法生成有效 StoryboardIR」；而错误信息用的是 schema 的语言（`String should have at least
20 characters`），**不会说「prompt 漏了这条」**。看到大量同一字段的同一种长度报错，先怀疑 prompt 没写。

**护栏**：
① 约束块从 `model_fields` 的元数据渲染，改了 schema 就改了 prompt——与「词表从 registry 生成」同一条原则；
② `test_storyboard_prompts.py` 断言渲染行里的数字集合 == 字段声明的边界集合（不是比对措辞，
   所以它不重复实现格式化，也能抓住「多出一个 schema 里没有的数」）；
③ `_CONSTRAINED_FIELDS` 表是手写的，但查表不是——字段改名会在测试里响，而不是在构造 prompt 时炸。

**同类前科**：`329dba7 fix(knowledge): align the coverage rule in the prompt with what the validator checks`。
这是第二次。所以这次不再逐条补措辞，改成**结构性**保证。

### D6 — `source_refs` 的两条规则必须能同时满足

**决定**：ref 有两条规则——对象要**覆盖**课程引用的每条 ref，且对象的每条 ref 要**存在于文档**。
当课程引用了文档里没有的 id 时，这两条会互相矛盾，必须显式化解：
**照抄课程不算编造**。合法 ref 集合 = 文档的 id ∪ 所覆盖课程场景的 refs（`_acceptable_refs`）。

**为什么**：两条规则各自都对，合起来却可能**无解**——模型必须引用它，又必须不引用它。
真实撞到过：一份**陈旧的 LessonIR**（文档后来被编辑过）让 prompt 里出现 11 条文档中不存在的 ref，
agent 把三次重试全烧在一个**没有任何输出能满足**的要求上，最后报「多次重试仍无法生成」。
**那条报错指向模型，真凶是校验台。**

**违反后的可观测症状**：同一场景反复重试、**报错数不收敛**（实测 7 → 15 → 11），
而模型的输出其实并没有越写越差。**看到「重试不收敛」，先怀疑要求本身可不可满足**，
别急着改 prompt——改 prompt 永远解不开一个无解的要求。

**护栏**：`test_a_lesson_ref_the_document_lacks_is_not_treated_as_invented`——
对象照抄课程的（含文档里没有的）ref，两条规则**同时**为 0；
而文档与课程**都不在**的 ref 仍被 `test_source_ref_unknown` 抓住，所以真的编造没有被放过。

## 踩过的坑

### 词表的两级结构被模型读成了一级

**症状**：`[unknown_role] `vector` 不是已注册角色` × 14，`axis`、`region`、`readout`、`trace`、
`dimension` 同样——模型填进 `role` 的是一整串**图元名**。

**真因**：词表原来这样渲染：

```
- `vector`（箭头…）：`velocity`、`force`、`displacement`
- `axis`（带刻度与标签的坐标轴）：`x_axis`、`y_axis`
```

冒号前是**图元**，冒号后是**角色**，而模型把整行读成了一张角色名单。
**这不是那份陈旧课程的问题——换任何域都会踩。**

**修法**：标题写明「`role` 字段只能填冒号后面的名字」；正文直说冒号前面是图元名、填进 `role` 会被打回；
行内改成 `- vector（…）→ 角色只能是：…`，让两级的排版本身不同。

**教训**：一份嵌套两级的清单，如果两级用同一种排版（都是反引号名字），读的人就会把它当一级。
**层级要靠排版区分，不能只靠标点。**

### 失败只留下 pydantic 的抱怨，留不下模型的原文

**症状**：一次失败只给你 33 行「某字段不符」，而**模型到底写了什么**完全不可见。

**为什么是坑**：`String should have at least 20 characters` 说了什么错了，**没说什么在那儿**。
于是只能对着一个数字猜：是模型写得太糙，还是这个数字本身就不对？
——而这两种情况的修法完全相反（改 prompt vs 改 schema）。第一次真跑时我正是卡在这里。

**修法**（已落地）：`StoryboardAgent(debug_dir=...)` 在每次重试前把**被拒的原文**落盘，
文件名带尝试序号。序号有用：对比 attempt 1 和 attempt 3，能直接看出**重试反馈到底有没有起作用**
——如果三次的错法一模一样，那就是 prompt 没说清，再重试也没用。
`service.py` 默认把 `output_dir` 传进去，所以走 CLI 就自动有。

> **补充（2026-09-14）**：这一条当时只补了一半——原文落盘了，**拒它的理由没有**。
> 理由只进了下一轮请求的 prompt，随进程一起消失。现在每次被拒写一对
> `…-attempt-N-raw.txt` / `…-attempt-N-error.txt`（旧名 `…-raw-attempt-N.txt` 已弃用）。
> 详见下文《拿不到 key 的时候》②。

**教训**：诊断信息的价值不在于「错在哪」，而在于「当时是什么样」。前者能读，后者只能猜。

### 推理模型把 `max_tokens` 吃光，正文为空

**症状**：`Storyboard Agent 多次重试仍无法生成有效 StoryboardIR：Expecting value: line 1 column 1 (char 0)`

**这个报错在骗人。** 它指向 JSON 解析，实际原因和 JSON 无关——模型**一个字都没吐**。

**真因**：`deepseek-v4-pro` 是**推理模型**，响应的 `message` 里除了 `content` 还有 `reasoning_content`。
`max_tokens` 是**推理 + 正文**的总预算。实测那份 storyboard prompt：

```
max_tokens=8192   → finish_reason=length, content len=0,      reasoning_tokens=8192  （全被推理吃光）
max_tokens=32768  → finish_reason=stop,   content len=12477,  reasoning_tokens=22662
```

**推理本身就用了 22662 个 token**，8192 连推理都不够，正文永远轮不到。

**修法**（已落地）：
- `llm.DEFAULT_MAX_TOKENS = 32768`，知识层与 storyboard 层共用这一个数。
- `LLMClient.chat` 遇到**空正文且 `finish_reason == "length"`** 时抛 `LLMBudgetExhaustedError`，
  错误信息直接说明是预算问题。
- 该异常**故意不继承 `ValueError`**：两个 agent 都是 `except ValueError` 重试，而同样的预算重试
  不可能成功——那会白烧两次又慢又贵的推理调用。

**为什么知识层这次没事**：它的 prompt 小得多，推理没吃满 8192，纯属侥幸。**潜在 bug 一直在。**
所以那个常量改成两层共用，而不是只调 storyboard 的值。

**教训**：`max_tokens` 在推理模型上不是"输出上限"，是"推理 + 输出"。看着像 JSON 错误的问题，
先确认模型到底有没有产出正文。

### 危险集合里装的是障碍物，不是车

**症状**：第一次跑无头冒烟检查，输出 `危险对象=obstacle-1,obstacle-2`——**危险的是障碍物**。

**真因（两个，叠在一起）**：

① `nearestDistance` 把节点自身也算进了障碍列表，于是每个障碍物到自己的距离恒为 0，
   永远低于阈值——**「危险」被永久钉在 on**。
② lookup 的 scene 层是无条件的，所以 `scene.safe_distance` 泄漏给了**每一个 body**，
   包括压根没有避障策略的障碍物。

**修法**：跳过自身；并把 `proximity_gate` 的适用范围**从 spec 推出来**而不是列出来——
按 registry 的语义，探测是 emitter 的活、阈值才是判定，所以该跑这个行为的是
**挂着传感器的那个 body**。没有传感器就没有危险态，而这正是障碍物应有的答案。

**教训**：这个 bug 不让任何东西报错，画面照样有东西在动。**它只是把一件事说反了。**
能抓住它的不是「有没有崩」，而是**把中间状态打出来看一眼**——冒烟检查顺带输出的那一行
才是真正的收获，`exit=0` 不是。

### ① 挂载物脱离母体——雷达扇与安全圈不跟着车侧移（**已修**）

**症状**：车躲开障碍物时，扇形雷达与检测射线**留在车道线上**，与车身脱开。

**真因**：`behaviors.js` 的避让趟跑在挂载趟**之后**，且遍历的是 `home`——**全部元素**，
不只是 body。它无条件执行 `node.y = base.y + next`，于是用**子元素自己的初始 y**
覆盖掉了前一趟刚设好的「子元素 = 母体坐标」。雷达因此横向跟着车走、**纵向被钉死在 y=310**。

**为什么难发现**：它不报错。画面照样在动，只是**一样东西和它本该贴着的东西分开了**。
这正是「会不会崩」这类检查抓不住、而人一眼看出来的那类缺陷。

**修法**：避让趟**只遍历 body**（非 body 本来就不该有 dodge），并把挂载趟**挪到最后**，
让挂载物在**同一帧内**落到母体真正到达的位置，而不是慢一帧。

**护栏**：`tools/player_smoke.mjs` 新增 `brokenAttachment()`，逐帧断言每个
`scene.attachment` 的 child 与 parent 坐标**严格相等**（两者只隔一次直接赋值，
任何漂移都是真缺陷而非浮点噪声）。同一条摘要里还输出 `最大侧移=xx px`——
**没有这一行，这个检查会空转通过**：车若从不侧移，「挂载物贴合母体」就和 `0 === 0` 一样为真，
什么也没证明。当前实测 `最大侧移=46.0px`，说明它确实在验。

### ② 高亮不够显眼，且第 2、3 拍看起来一样（未修，记录）

**症状**：高亮变化弱；第 2 拍（`lidar` + `obstacle-1`）与第 3 拍（`car` + `obstacle-1`）
看上去相同。

**诊断**（已定位，未动手）：
- `primitives.js` 的 `applyHighlight` 只设 `shadowColor` / `shadowBlur`。这对 `drawBody` 有效，
  对 `drawEmitter` **几乎无效**——扇形填充是 `rgba(66,247,255,0.08)`，淡到辉光看不出来；
  而射线紧接着**自己改写了 `globalAlpha`**，辉光也落不到射线上。**高亮 `lidar` 等于没高亮。**
- 第 2、3 拍唯一的**可见**高亮都是 `obstacle-1`——**不是高亮没换，是换掉的那一个看不见。**

**修法方向**：高亮不能只靠辉光。让高亮同时改变**自身**的线宽/亮度，并**压暗未高亮的对象**——
对比度来自落差，不是来自一味加亮。

### ③ 避让是「擦着过去」；障碍物 B 从不触发（未修，记录）

**症状**：车看起来没完全避开障碍 A；障碍 B 全程无需避让。

**障碍 B 是原文件就有的，不是适配器发挥的。** `animation/templates.py:24-25`（冻结基线）：

| 元素 | 中心 y | 离车道 | 判定 |
|---|---|---|---|
| `obstacle-1` | 300 | **10px** | 几乎压在车道上，必躲 |
| `obstacle-2` | 210 | **100px** | 100 > 安全距离 76 → **永不触发** |

车在 y=310、安全距离 76。`obstacle-2` 是**纯布景**——这与「装饰性对象与 `orphan_object`
有张力」是同一件事的两面。

**「没完全避开」的数字是我定的。** `behaviors.js` 的 `MAX_DODGE = 46` 是拍出来的常数，
而基线把障碍 A 放在离车道仅 10px 处。按当前数字算，车躲到最远处时车身边缘与障碍 A 边缘
**只剩约 2px 余量**——几何上过了，读起来是蹭过去的。

**修法方向**：避让幅度不该是常数，应由「车身半宽 + 障碍半径 + 安全余量」算出；
且避让的**触发时机**要早于「最近距离 < 安全距离」的那一帧，否则先贴近、再躲开。
**M2 的浏览器验收把这条的根因挖出来了**（上下判据用了车当前的 y，正反馈无回复力），
完整机制与量化数据见 M2 一节末尾——那里同时给出了第 ① ② ③ 步修法。

**这三条都不阻塞 M2**——M2 的输入是手写 sample，输出是坐标；② ③ 全在**播放器的行为层**，
与布局层不相干。但 ① 必须先修，因为后面每个预设都会继承同一个行为层。

## M2 学会自己摆：`lane` 的确定性布局（2026-09-13 完成）

`rendering/layout.py`：`StoryboardIR`（纯语义、无坐标）→ `RenderSpec`（含坐标）。
判据是**「手写 sample → RenderSpec → 与 M1 画面同义、并排可对照」**，验收如下。

### 比例用的是基线自己的分数，不是四舍五入的近似

车道 `310/600`、车 `120/960`、第一根障碍 `410/960`、间距 `160/960` —— **把基线的分子分母
直接写进常量**。初版写的是 `0.52` / `0.12` / `0.42`，看着更整洁，代价是第一根障碍会落在
离 `templates.py` 6px 的地方。并排对照要回答的是「差在布局还是差在绘制」，
**几像素的偏移正好是两边都赖得掉的量**，所以宁可把分数原样写进代码。
实测摆出来的车就在 `(120, 310)`，与基线逐点相同。

### 障碍物改成一上一下——这是相对基线的**有意**改动

基线把两个障碍都放在车道上侧（y=300 与 y=210），于是「比较左右空旷度」这一拍
**永远得出同一个结论**。`lane` 改成上/下交替，第四拍才有得比。
**改的是排布意图，不是基线的数字**——基线的数字一个都没动。

### 一条跨层约束：`offset + MAX_DODGE > safe_distance`

这是布局常数与播放器常数的乘积，**两层各自看都挑不出错**：

| 量 | 值 | 出处 |
|---|---|---|
| 障碍离车道的距离 | `safe_distance × 0.5` = 38px | `layout.py` |
| 小车最大侧移 | `MAX_DODGE` = 46px | `frontend/player/behaviors.js` |
| 安全距离 | `safe_distance` = 76px | scene param |

三个数凑在一起才决定第四拍**到底有没有发生**：障碍离得太远 → 车根本不进危险态，
没有避让可看；离得太近 → 再怎么躲都出不了危险圈，**画面照常在动，所以看不出坏**。
`test_the_car_can_escape_the_danger_envelope` 从 `behaviors.js` **正则读出** `MAX_DODGE`，
两个不等式一起断言，两层因此无法各自漂移。

**它同时给出了浏览器验收遗留问题 ③ 的精确诊断。** 冻结基线把 `obstacle-1` 放在离车道
**10px** 处，`10 + 46 = 56 < 76` —— **基线自己过不了这条不等式**：小车躲到最远处仍留在
危险圈内，于是 `danger` 恒为真、避让动作顶在最大幅度不动。用户看到的「小车没能完全避开
障碍 A」，在数字上就是这一句。`lane` 摆出来的 38px 落在**能出圈**的那一侧
（`38 + 46 = 84 > 76`）。

冒烟检查把这个差别直接显示出来了：摆出来的 spec 侧移到 **38.5px 就出了危险圈并回正**，
基线 spec 则**顶在 46.0px 不动**——正是一条不等式的两个方向。

这**不构成对基线的修改**（`templates.py` 冻结）。要改的是播放器侧那条「贴着边界来回蹭」
的行为（避让幅度应由几何算出、触发时机应早于「最近距离 < 安全距离」那一帧），
已记在 ③，属于 M2 之后的打磨，不阻塞。

`assets/glyphs/` 目前**没有**。`layout.py` 读这个目录决定要不要给 `body` 发 `glyph` 字段——
数据不在就退回参数化形状（障碍物是 8 顶点星形，与 `app.js:696` 同构），但**请求的名字原样
留在 `props.glyph` 里**，所以缺口在 spec 里看得见，不是悄悄消失。
两条测试把「数据一落地就自动生效、布局代码一行不改」这句承诺变成可执行的断言。

- `test_the_laid_out_spec_round_trips_through_json_unchanged`：规范化不动点。

### 浏览器验收发现的新问题：安全距离一动，避让就失效（记录，**未修**）

**症状**（用户报告）：摆出来的那份比基线好，但**一调「安全距离」，小车就乱**，
第二个障碍物完全躲不掉。

**这不是精度问题，是一个确定的缺陷，已经量化。** 冒烟检查现在每次都会打印两个数——
默认安全距离、以及把滑杆拉到上限时，车离每个障碍物最近到过多少
（相切阈值 = 车身半宽 31 + 障碍半径 32 = 63px）：

| spec | 默认安全距离 76 | 安全距离拉到上限 120 |
|---|---|---|
| 布局 | `obstacle-a` 71px、`obstacle-b` 71px | `obstacle-a` 84px、**`obstacle-b` 8px** |
| 基线 | **`obstacle-1` 54px**、`obstacle-2` 100px | `obstacle-1` 56px、`obstacle-2` 119px |

`8px` 就是「从障碍物身上开过去」。基线那格 `54px < 63px` 则说明它**在默认设置下就已经穿模**——
这正是用户最初说的「小车没能完全避开障碍 A」。

**机制**（读 `behaviors.js` 的 `sideClearance` 得出，与轨迹吻合）：
它用**车当前的 y** 判断一个障碍物在车的上方还是下方：

```js
if (other.y <= node.y) above = Math.min(above, room); else below = ...;
```

而车的 y 正是避让要改的量。车为了躲 `obstacle-a` 往下挪 46px 之后，**`obstacle-b`（y=348）
就落到了车的上方**（车 y=356），于是 `below` 重新变回 `Infinity`、`above > below` 为假，
目标继续是 `+MAX_DODGE` —— **车被命令继续朝它已经在走的方向躲下去，而那个方向正是 `obstacle-b` 所在的地方。**
这是一个没有回复力的正反馈：判据随着结果一起变。

轨迹佐证：安全距离 120 时**方向翻转次数 = 0**，侧移**顶在 46.0px 不动**，
而 `obstacle-b` 就在 8px 外。安全距离 76 时翻转 3 次——车在 `obstacle-a` 前下躲、
到 `obstacle-b` 前又上躲，两次反向，**用户读到的「乱」就是这个**。

**为什么只有拉大安全距离才暴露**：车要出圈需要 `侧移 > safe_distance - 38`。安全距离 76 时
门槛是 38，`MAX_DODGE` 46 够；拉到 120 时门槛是 82，**46 永远不够**，于是车恒在危险态、
恒被命令「继续躲」，而 `sideClearance` 的判据又已经失效。

**修法方向**（三步，都属于 ③ 那条「避让应由几何算出」）：
① 判定上下要**用固定的车道线**，不能用车当前的 y——判据不能依赖它自己要产生的结果；
② 侧移幅度由「车身半宽 + 障碍半径 + 安全余量」算出，不用常数；
③ 每一根障碍物**只选一次边**，不要每帧重选。

**为什么现在不修**：它整个落在**行为层**，与布局层无关——`layout.py` 摆出来的几何是对的
（`offset=38` 在默认值下可出圈，两个障碍一上一下）。当前优先级按用户指示是「产出雏形、
能稳定地对各种文档生成动画」，这条与 ②③ 一起排在精度打磨阶段。**冒烟检查已经在每次运行里
把数字打出来**，所以它是一条被测量的已知缺陷，不是一句会烂掉的话。

## M4 首跑：真文档走通了，并且立刻暴露了三件事（2026-09-13）

### 发现的第 1 件：布局按「角色名」判断谁是链路成员，太窄了（**已修**）

模型把文档里的「激光雷达**节点**」写成了 `role: "device"`。`chain` 当时按
`role == "node"` 决定谁上脊线，于是它被摆到下面的驱动行，**那条 `scan-topic` 就从左下角
斜穿整张图连到右上角**。什么都不报错，图只是突然不能看了。

改成**结构判据**：`_link_endpoint_ids()` —— **有 link 连到它，它就是链路成员**，
不管模型叫它什么；没有 link 连的才是被驱动的东西（正是下面那一行的含义）。
修完 `cmd-scan-workflow` 四个 body 齐刷刷排在一条水平脊上，两条 link 都是短线：

```
control-node(153.6) → cmd-vel-topic → chassis-node(371.2) → lidar-device(588.8) → scan-topic → avoidance-node(806.4)
```

`test_a_chain_participant_belongs_on_the_spine_whatever_its_role` 看住这条。

### 发现的第 2 件：词表给了属性名，**没给量纲**——这是根因（记录，未修）

同一个根因的三个症状，全都在真实产物里：

| 症状 | 真实值 | 应有的量级 | 后果 |
|---|---|---|---|
| `scan-emitter.radius` | **3.0** | 基线雷达是 **150** | 半径 3px 的扇形，在 960px 画布上**等于没有** |
| `cmd-vel-msg.speed` | **40.0** | 令牌速度 `progress = (t×speed)/2 % 1` | 16 秒里绕 **320 圈**，看不见移动 |
| 滑杆 default vs 物体 prop | 滑杆 5.0 / 物体 3.0 | 两者应相等 | 播放器启动时写 override，**画面一载入就和布局画的不一样** |

词表里 `radius` 只是 `emitter` 的一个 prop 名，`speed` 只是 `traveler` 的一个 prop 名，
**没有任何地方告诉模型这些数是画布像素、量级大概多少**。模型只能猜，猜出来的数
与 960×600 的舞台差一到两个数量级。

**这不是「模型不行」**，与 `generic` 那次是同一类问题：**契约没说的东西，模型不会知道**。
修法是让词表声明量纲与量级（`radius`：画布像素，常见 60~200；`speed`：每秒走完路径的比例，
常见 0.2~1.5），并在 prompt 里写明。**校验台抓不住这个**——3.0 是完全合法的 `radius`。

### 发现的第 3 件：滑杆 default 与物体 prop 谁也没对过账（记录，未修）

上表第三行。`control_range_invalid` 只查 `min < max` 与 `min <= default <= max`，
**不查 default 与目标对象自己那个 prop 是否一致**。不一致的后果已经有过一次同构的先例：
安全距离圈不跟着滑杆动（见 M1 遗留问题 ①）——**标签和东西对不上，只有人会看出来**。

修法：校验台加一条 `control_default_conflicts_with_prop`。**这条故意没做**：
加上去之后上面那份真产物会**校验失败并重试**，而那正是想要的
（「让生成失败，而不是交给人眼发现」），但它会改变真实生成的成功率，
值得单独一步做完并观察，不塞在首跑的尾巴上。

### 关于「手写 sample 有什么用」

真实运行恰恰说明了它有什么用。第 1 件事——脊线判据太窄——**是真跑才能发现的**；
但发现之后要判断「是布局错了还是模型选错了角色」，**需要一个已知正确输入的对照**。
`ros_pub_sub.json` 就是那个对照：它证明 `chain` 在模型不捣乱时画得对，
于是问题被定位在「布局的判据太窄」，而不是「chain 整体不行」。

反过来也要说清楚：**手写 sample 证明不了模型会写出这种东西**，
而第 2、3 件事全是模型侧的问题——**只有真跑才看得见**。两者不是替代关系。

## M3-b 完成：`hub` + `field`，以及四个只有它们用得到的图元（2026-09-14）

这一步的需求**不是设计出来的，是真链路要出来的**。先跑一遍三份样例文档：

| 文档 | 结果 |
|---|---|
| `ros_pub_sub.md` | 退出码 0（M4 那次已经通过） |
| `robot_obstacle_avoidance.md` | **布局失败**：`scene-1` 选了 `hub`，没有实现 |
| `projectile_motion.md` | **布局失败**：`scene-1` 选了 `field`，没有实现 |

抛体那份的 8 个场景里 **7 个选了 `field`**，避障那份两个场景选了 `hub`。三份文档只出得来一张图。

这不是模型乱选——`hub` 和 `field` 就是这两份文档的正确预设（避障文档讲的是「底盘 / 电机控制器 / 激光雷达 / 避障程序」四个部件，就是星形；抛体文档整篇是二维场）。
**词表提供了名字，布局层没有实现，于是生成失败在一个 prompt 里读不出来的原因上**——和 `generic` 那次同构，只是方向相反。

### `hub`：中心 + 环，但**不替模型连辐条**

中心取第一个 `node` 角色（`required_roles` 已经这么承诺了，校验台保证它存在），其余 body 均分在椭圆环上。

环是**椭圆不是圆**：960×600 的舞台上，按高度定半径会横穿到右侧说明栏，按宽度定半径又会挤成一条竖线。x 半径 0.22 就是被说明栏逼出来的——0.30 时最右边那个叶子会和面板重叠，那是 `LayoutError`，会让整场失败而不只是拥挤。

**辐条不生成。** 一条边是模型该写的东西：它想让中心连到叶子上就该写 `link`，不写的话画出来的是**花瓣**——那就是它画的东西。在这里补线等于往画面上加没有节拍指向的线。

### `field`：一个真实文档逼出来的两个关键决定

**① 方向有两套约定，转换只准发生在一个地方。**
`lane` 里的 `heading` 是画布约定（0=右，顺时针，y 向下），播放器的 `drawHeading` 直接读。但抛体文档写的是 `heading: 90` 表示「竖直上抛」、`direction: -90` 表示重力向下——那是**物理约定**（y 向上）。照画布约定读，这两个会分别指向地面和天花板。

`atoms.js` 开头就写了「调停两者是布局层的活，不是渲染层的」，于是有了 `_to_canvas_angle()`——**全工程唯一做这个转换的地方**。

**② 轨迹用固定初速度画，不是「把最大的弧塞进盒子」。**

这条是被一个测试逼出来的。第一版按「顶点尽量高、总长按槽位截断」来画，测试断言「角度越大射得越矮」，结果 30° 和 60° **宽度一模一样**。

宽度的答案本该是：文档自己的【四、注意事项】写着「发射角 θ 与 (90°−θ) 的射程完全相同，其中 45° 时射程最大」「竖直上抛射程为 0」。按固定初速度 `v`：
`R = v²sin2θ/g`、`H = v²sin²θ/(2g)`——**30° 与 60° 落点相同、45° 最远、90° 射程为零**，三条都是课文原话。而「塞满盒子」的规则会把这三条**全部画反**。

现在的实现：45° 的射程恰好铺满该 body 的槽位，其余角度由上面两式导出。轨迹的抛物线开口斜率恰好等于 `tanθ`，所以画出来的曲线和课文里的数是一致的。
四条测试看住它：互补角等射程、角度越大越高、45° 最远、90° 射程为零。

### 矢量的长度：**不要跨量纲对齐**

场景 1 同时画了 `v0`（50 m/s）和重力（9.8 m/s²）。按数值等比例画，重力只有速度的五分之一长，读起来像装饰；但**更大的问题是这个比例本身没有意义**——两个量纲不同的量本来就不可比。

规则：**在同一场景内归一化**（最大者取满长度，其余按比例），外加一个下限 `VECTOR_MIN_FRACTION = 0.35`。
- 分解图里 30 : 40 保住了 0.6 : 0.8（这是课文里那个直角三角形的事实，必须保）；
- 单独一个重力不会被画成一个点。

### 其余四处

- **说明栏面板高度改成按数量自适应。** 抛体文档的「关键参数」场景是 **7 张符号卡**，按默认 88px 排不进 432px 的栏里，第一版直接因为重叠 `LayoutError` 了——**一个场景唯一的过错是话比较多**。`_column` 早就是按数量均分的（它的 docstring 写着这是为了任何数量都待在画布内），只是面板高度没跟着走。
- **超范围的值夹住，不抛出去。** 真链路写了 `fov: 0`（雷达还没开始扫描），`EmitterElement` 的 `gt=0` 直接拒绝，pydantic 的报错**越过了布局层**变成一条 traceback，指名一个字段而不指名哪个对象、哪个场景。现在 `layout_scene` 里有一道兜底：任何元素构造失败都转成 `LayoutError` 并带上 `scene.id` 与 `obj.id`——**CLI 认得的那种错误**。`fov` 本身按契约范围夹住。
- **`dimension` / `vector` / `trace` 带上它们挂靠对象的 id。** 布局把坐标烤进 spec，但播放期母体会动——不带 id，小车开走了标注线还留在原地。这与安全距离圈那次是同一类失败（**标签和东西对不上**）。
- **`region` 与 `wave` 仍未实现，且是故意留的。** 它们没有出现在任何一份真实产物里，**凭空实现的图元正是「看着合理但是错的」画面的来源**。播放器会指名道姓地拒绝，不会画一个猜测。（2026-09-14 补：**只在播放器拒绝是不够的**——见「登记 ≠ 能画」。）

### 真链路紧接着暴露的第六件事：属性**没写**，不是写错

重跑抛体文档（新的 lesson 只有 5 个场景）后，模型给出的对象是这样的：

```
v0_vec   velocity   {'of': 'projectile'}          ← 没有 magnitude，没有 direction
x_axis   x_axis     {}                            ← 没有 ticks
theta_angle angle   {'of': 'projectile'}          ← 没有 degrees
```

一个都没报错：布局层有默认值，画面照样出来。但**那支「初速度」箭头是水平的**（`direction` 默认 0），而这一课讲的正是斜抛。

这和第 2 件事（量纲）是同一个根因的另一半：**词表声明了一个属性的名字，没有说这个属性是「可以写」还是「应该写」，也没有说写了之后那个数是什么量纲**。
修法是把词表从「属性名清单」升级成「属性说明」——单位、常见量级、以及缺省时画面会退化成什么。

同一份产物还暴露了第二个缺口：`scene-5` 同时有 `ideal_trajectory` 与 `drag_trajectory`，两个都挂在同一个 body 上、都没有 `length`，
于是**画出来是两条完全重合的抛物线**——而这一课讲的正是「空气阻力让射程明显变小」。**画面说了课文的反面。**
词表里没有任何东西能把「理想」和「真实」区分开（两者 role 都是 `trajectory`，可用的属性只有 `length`/`visible`）。这是词表缺口，不是布局缺口。

**2026-09-14 更正一半：「属性没写」这一条没有复现。** 充值后重跑，`v0` 写全了 `magnitude`/`direction`，`x_axis` 写全了 `range`/`ticks`，`angle` 写全了 `degrees`，而且数值是对的（详见下节）。所以当时那段是**采样方差**，不是系统性倾向——把它当成「模型爱漏写」会误导 M4 跟进 1 的排序。**仍然成立的是量纲那一条**，而且它不需要假设模型会漏写：一个写全了的 `radius: 8` 依然是 8 米被读成 8 像素。「理想 vs 真实轨迹」那个缺口也仍然成立（这一轮的 `scene-5` 只剩一条 `trace`，因为它没再同时写两条——同样是采样方差，而缺口的成因与采样无关）。

## 登记 ≠ 能画：把终局失败提前成一次重试（2026-09-14）

用户点头的是「补 `region`/`wave`」，落地的却是「**不把它们递给模型**」。理由是一句承诺：词表里出现一个名字，就是对模型说「写它，画面会出来」。

**失败链本来是终局的。** `render_vocabulary()` 遍历**全部** T1 图元渲染提示词，于是 `area`/`band`/`waveform` 这些角色名被主动递出去；校验台也放行（它只查角色认不认识，不查这个图元画不画得出来）；一直到布局层才抛 `LayoutError`。关键在于**布局跑在最后一次 LLM 调用之后**——校验失败会被回灌成「上一次输出校验失败：…」让模型重试，布局失败不会，那条路径已经出了 agent 循环。后果不是画面糙了，而是**一份讲简谐振动或阴影面积的文档一张图都出不来**，且报错里出现的是图元名而不是那份文档。

**这也不是两个名字的问题。** 有测试断言每个预设都有布局实现，**没有**对应的「每个图元都有布局实现」。`region`/`wave` 只是当前站在洞那一侧的两个名字；下一个加进 `registry.py` 的图元会一模一样地重演。

**改法的形状：一处声明，三边读取。** `Primitive` 增加 `drawable`；`PENDING_PRIMITIVES` / `PENDING_ROLES` / `PENDING_ALTERNATIVES` 全部由它派生。布局层、校验台、提示词读的是同一个来源，所以它们不可能各说各话：

- **布局层**先查 `PENDING_PRIMITIVES` 再分派，错误里给出能替代的角色（`band` → `zone`/`dimension`，`waveform` → `trace`）。分派链最后的兜底改成了一条**内部矛盾**的报错——走到那里说明注册表声称能画而这个函数不认，要改的是 `registry.py`，不是分镜。
- **校验台**新增 `primitive_not_drawable`，把终局失败提前成**一次可重试的校验失败**：模型看到报错、改写成 `zone`，画面照样出来。
- **提示词**不再提供这两个图元，但**明确说它们存在、当前不可用、以及该写什么**。直接删掉名字更糟——模型会再猜一次，把一个重试花在「这个词为什么不是合法角色」上。

**一处刻意的取舍：** `region.bounded_by` 仍留在 `REQUIRED_RELATIONS` 里（它是**画法**的事实，不是**可用性**的事实），但提示词不再为它渲染属性行。于是那条「每个必需关系都要在提示词里标出『必须填写』」的测试改成只遍历 `drawable` 的图元——不改的话，它会因为一个**刻意不展示**的图元变红，而它的本意是抓「约束只活在代码里、模型从没被告知」。

**四条守卫，其中一条原来的写法是绿在错的地方：**

- `test_vocabulary_does_not_offer_a_primitive_that_cannot_be_drawn`——**结构性**断言。原来那条只问「这个名字有没有出现在文本里」，而 `region`/`wave` 一直**出现在文本里**（出现在那张禁用它自己的清单里），所以它是绿的。现在断言的是：角色清单里只出现 `drawable` 的图元，且每个 pending 的名字都出现在「不要用」那一段、带着它的替代表达。**一个名字是被一行提供它的文字提供的，不是被文件里含有这个字符串提供的。**
- `test_every_drawable_primitive_reaches_a_converter`——`drawable=True` 是给分派链的承诺。它逐个图元调 `_to_element`（空盒表，多数会因缺几何而抛错，这不影响结论），断言失败**不是**「注册表与布局层不同步」那一条。`registry` 与 `layout` 谁滑了都会先在这里红。
- `test_every_pending_primitive_says_what_to_use_instead`。
- 校验台的 `test_primitive_not_drawable`，同时断言**不是** `unknown_role`——名字是真的，谎称它不存在会让模型去找一个不存在的错别字。

### 充值后重跑：三份文档第一次全部出图（2026-09-14）

三份样例一次跑通，各产出一份可播放的 `RenderSpec`：避障 68 次绘制、ROS 80 次、抛体 96 次，`player_smoke.mjs` 全部无异常。`hub` 与 `field` 都落到了真链路上——避障第一幕是 **8 元素的 `hub`**（中心节点 + 四个叶 + 挂在叶上的雷达扇与区域），抛体 5 幕全是 `field`。**M3-b 那两个预设在真产物里第一次有画面可看。**

**量纲的问题这一轮有了可测量的证据，不再只是「看着不对」。** 同一份避障文档的两幕：

```
hub  幕：lidar_emitter.radius = 8      ← 模型写的是文档里的「8 米」
        front_zone.radius    = 8      ← 布局读成 8 像素
lane 幕：safe_zone.radius     = 0.8    ← 「安全距离 0.8 米」→ 0.8 像素
        left_space / right_space = 1.2 / 0.9（第 3 拍设的）← 都不到一个像素
```

后果由冒烟工具直接读出来：`avoidance-decision` 一幕 **最大侧移 0.0px、运行中从未进入危险态**。障碍物离车 38px，危险阈值 0.8px，于是**邻近判定永远不触发、车永远不避让**——`lane` 预设与 `clearance_choice` 行为存在的理由整个失效。第 3 拍（「左右空间比较」）把左右的 `radius` 设成 1.2 与 0.9，**两个数都画不出一个像素**，这一拍承诺的视觉变化在画面上不存在。滑杆 `safe_zone.radius` 的范围 [0.2, 2.0] 是**米**，无论拉到哪端都画不出可见的圆。

一句话：**词表里的 `radius` 没有量纲，于是同一个词在模型眼里是米、在布局眼里是像素**，两边都不报错。这是 M4 跟进 1 的直接输入。

**另一处在真产物里确认：`enabled` 被声明，但无人读取。** `hub` 幕第 3 拍的旁白是「画面中的扫描波束随周期闪烁一次」，`object_states` 里写了 `lidar_emitter.enabled = false`——而**没有任何图元或行为读 `enabled`**。这一拍承诺的闪烁不会发生，校验台也拦不住（它只查控件绑定，不查节拍）。这和「滑杆 default 与物体 prop 谁也没对过账」是同一类：**断言了，却没人消费**。

## 声明 ≠ 会动：20 个死节拍，以及让它们动起来（2026-09-14）

用户打开两个播放器链接，反馈是「**连动画效果都没了，而是两张图**」。实测证实了这句话，而且比它更严重。

**先量，不猜。** 用与 `player_smoke.mjs` 同样的推进方式（每拍跑 3 秒，逐元素量最大位移）：

| 场景 | 预设 | 会动的元素 |
|---|---|---|
| 避障 `system-lidar` | hub | **无** |
| 避障 `avoidance-decision` | lane | car / safe_zone / left_space / right_space（后三个只是跟着车平移） |
| 抛体 scene-1 ~ scene-5 | field | **全部无** |

**7 个场景只有 1 个会动。** 再把每个节拍写下的 `object_states` 逐条对到「有没有代码读它」：

| 文档 | 节拍写下的状态 | 没人读取的 |
|---|---|---|
| 抛体 | 19 | **17**（`vector.direction`×7、`vector.magnitude`×4、`angle.degrees`×4、`trace.length`×2） |
| 避障 | 10 | 3（`emitter.enabled`×2、`body.danger`×1） |
| 合计 | 29 | **20** |

最刺眼的一处：抛体 scene-1 的五拍讲的就是「初速度方向不同 → 平抛 / 斜抛 / 竖直上抛」。模型写得**完全正确**——`direction` 依次 `0 / 45 / 90`，一条都没错，而 `drawVector` 画的是：

```js
const tipX = node.x + element.dx;   // 从不调用 view.lookup
```

箭头纹丝不动。**模型对了，schema 对了，校验台也放过了，画的时候没人读。**

**这是上一轮那条命题的下一层。** 上一轮是「**登记 ≠ 能画**」（`drawable` 门禁）；这一轮是「**声明 ≠ 会动**」——一个属性被声明、被校验台放行、被节拍赋值，却没有任何渲染代码消费它。

### 四类根因

**① 节拍的状态没有消费者（20/29）——最大的一条。** `view.lookup` 是节拍改变画面的**唯一通道**，而只有五个绘制函数走它（`drawEmitter`/`drawZone` 读 `radius`、`drawLink` 读 `active`、`drawReadout` 读 `text`，加上两个行为读 `speed`/`safe_distance`）。其余一律直接读烘焙好的数字。

关键事实：`layout.py` 的每个转换器都以 `props=dict(obj.props)` 结尾，**属性原样留在 spec 里**——播放器看得到 `direction`/`degrees`/`length`，只是没人读。所以这一条**不需要改契约**，只需要绘制函数改读 `lookup`，烘焙值退化为兜底。

**② `field` 没有任何运动行为。** `ballistic` 是按计划推迟的，于是抛体的 5 幕**从构造上**就是静图：`_arc_points` 明明已经把弹道算出来了（49 个采样点），但它只喂给 `trace`，**球本身不在上面走**。

**③ 避障那一幕的危险判定是死的。** `behaviors.js` 从**车身**上找阈值（`lookup(bodyId, "safe_distance")`），走查表第 4 层 `scene.params`。手写基线样本正好把 `safe_distance` 放在那里，所以基线是对的；而真文档里模型写的是 `safe_zone.radius`——`car.safe_distance` 不存在、`scene.params` 是 `{}`，于是 `continue` 掉每一帧，**危险永不触发，避让也永不触发**。小车只会匀速右滑。文档讲的是避障决策，而决策没有发生。

**④ 量纲。** 同一个词，模型眼里是米、布局眼里是像素（上一轮已量过，见上）。`hub` 那一幕的全部内容是「激光雷达扫描前方 180°」，而它画成了一个 16 像素的斑点。

### 改法：一处声明，四处消费

**`Primitive.live_props`** 声明「哪些属性在播放期真的会被读」——`props` 回答「能不能设」，它回答「设了有没有用」。它与 `drawable` 是同构的两个问题，失败也是同一种：`drawable` 低了会让整份分镜在布局层作废，`live_props` 低了会让一整拍在屏幕上静止，**两者都不报错**。

- **校验台**新增 `step_state_inert`：节拍的 `object_states` 只能动 `live_props` 里的属性。**只对 `object_states` 生效，不对 `obj.props` 生效**——`glyph` 本来就不该逐拍改，`direction` 本来就该。这一条把今天的 20 个死节拍全部变成一次**带解释的重试**。
- **提示词**把属性分成「可被节拍改变」与「只能整体设置一次」两组。这不是新规则，是把**已有的区别第一次说出来**。
- **`registry.js` 手写一份 `LIVE_PROPS`**，Python 测试断言两边**逐键相等**。手写而非派生，正是为了让「两边不一致」变成一个红测试——和 `PENDING_KINDS` 同一个理由。

**八个绘制函数改读 `lookup`**：`vector` 的 `direction`/`magnitude`、`angle` 的 `degrees`、`trace` 的 `length`/`visible`、`axis` 的 `range`/`ticks`、`body` 的 `heading`/`danger`/`visible`/`scale`、`emitter`/`zone` 的 `enabled`、`dimension` 的 `label`、`readout` 的 `tone`、`traveler` 的 `progress`/`state`。

两个比例**由布局烘焙下来，不在 JS 里重算**：`VectorElement.length_scale`（矢量长度是**场景内**归一化的，最大 `magnitude` 拿满长度）与 `TraceElement.length_reference`。让 JS 重述这条规则就是两处实现、必然漂移。

**`field` 拿到运动。** `layout._flight` 把 `_arc_points` 算出的抛物线挂到球身上（`BodyElement.path` + `duration`）——**与 `trace` 是同一条曲线**，所以「课里画的轨迹」和「球飞的路径」不可能不一致。播放器只做插值，**不做任何物理**（D3）。`duration` 由弧长除以 `THROW_PIXELS_PER_SECOND` 得出，所以 45° 与 15° 是同一次投掷，长弧就是飞得久。

**`RenderScene.thresholds`** 把 body id 映到挂在它身上的 `safe_distance` 角色 zone——**由场景图推导，不问模型怎么写属性名**。这是 ③ 的修法，和 `_chain_boxes` 问「有没有 link 碰它」是同一个动作。同时 `_lane_boxes` 的障碍物偏移改成读**同一个数**：偏移量与危险阈值本来就该同源，两个来源意味着「车在一个距离上反应、障碍物按另一个距离摆」。

顺带：`proximity_gate` 不再要求场景里有 emitter。阈值是**判断**，不是传感器——避障那份的决策幕正是「有车、有阈值圈、有障碍物，没有雷达」。

### 顺带堵掉的一个终局陷阱

词表写着 traveler「沿 link **或 trace** 移动」，而 `_to_traveler` 只认 link，`along` 指向 trace 会抛 `LayoutError`——**布局跑在最后一次 LLM 调用之后**，于是一条提示词承诺、代码拒绝的路径。改掉措辞之外，校验台新增 `relation_wrong_kind`：引用解析得开不等于布局用得动。

### 冒烟工具自己也有同一个盲点（这一段是这一轮最有用的意外）

新增的运行期检查是「**任意相邻两拍画出来的调用序列不得完全相同**」——`step_state_inert` 在运行期的孪生检查，一个查契约、一个查实际画出来的东西。

第一次跑它就报了 `avoidance-decision` 的 step-5 静止，而**这是误报**，且是它自己的两个缺陷：

- `fakeContext` 的 `record` 往 `calls` 里塞的是 `{name, args}` 对象，而新检查用 `calls.join("|")` 序列化——每个调用都变成 `[object Object]`，**两拍永远相等**。换句话说：一条用来抓「画面没变」的检查，因为看不见画面而恒真。修成显式序列化。
- 更根本的一条：它把样式赋值记成了普通字段。而 `applyHighlight` **只**设 `shadowColor`/`shadowBlur`——**高亮就是一次样式变更**。不记样式，就等于把「绝大多数节拍唯一的动作」从记录里抹掉。改成 `defineProperty` 记录赋值。

原始注释「样式属性只会被赋值、不会被读回，所以普通字段够用」在写它的那天是对的，在这一轮变成错的：**检查读的是什么，决定了记录必须记什么。**

**① `cli.py:140` 报错写的是「请在 .env 或环境变量中设置」，但 `src/` 里没有任何代码打开过 `.env`。**
这句话指着一个没有读者的文件——把 key 放进去会被无声忽略，而且不报错。
`llm.py` 新增 `load_env_file`（在 `load_llm_config` 里调用，不在 import 时调用，
以免 import 这个模块就悄悄改了进程环境），**已存在的环境变量永远优先**：
一个显式 `$env:DEEPSEEK_KEY` 是刻意的覆盖，工作区里的旧文件不该偷偷盖过它。

成对的价值在于：原文说模型做了什么，理由说校验台怎么答的，**只有合起来才能回答

### ② 量纲：m5 真的踩了，r2 修好了

|---|---|---|

### ③ 模型没有靠「少写状态」蒙过门禁——方向正好相反

这是重跑前最该担心的事：`step_state_inert` 只保证**写进去的**属性能动，
不保证模型**还在写**。模型完全可以清空 `object_states`、只留 `highlights` 来满足它——
那样每条门禁都绿，画面却更糟。

| 文档 | `object_states` 总数 | 只有文字、没有任何状态的节拍 |
|---|---|---|
| ros_pub_sub | 3 → **18** | **11 → 1** |
| robot_obstacle_avoidance | 9 → **22** | 3 → 0 |
| projectile_motion | 17 → **47** | **10 → 0** |

旧规则是「高亮**或**状态」二选一（`_must_change_something`），模型就用 `highlights` 满足了它。
**门禁的漏洞不是它放过了坏输出，而是它认可了一种「合法但什么都不写」的写法。**

### ④ 「会不会动」得换一把尺子，而且功劳不能全算给提示词

`player_smoke.mjs` 的「相邻两拍不得完全相同」**看不出高亮**：`applyHighlight` 只设
`shadowColor`/`shadowBlur`，而 harness 把样式赋值也记进调用（见上一节「冒烟工具自己也有同一个盲点」）。
于是一个「换个元素发光」的节拍照样算「有变化」——**那一节把这条记录在案，但没有量过它有多要紧**。

现在量了。把样式赋值全部剔除、只比几何与文字：

| 文档 | 旧 storyboard + 旧布局 | 旧 storyboard + **新布局** | **新 storyboard** + 新布局 |
|---|---|---|---|
| projectile_motion | 14/19 静 | **0/19** | **0/17** |
| robot_obstacle_avoidance | 1/8 静 | 1/8 | 1/9 |
| ros_pub_sub | 1/11 静 | — | **0/12** |

分母是**相邻节拍对数**，不是节拍数。一幕的第一拍没有上一拍可比，**永远不可能**
「与上一拍相同」，把它的位置算进分母等于在分母里垫了一个注定为真的数——`obstacle`
那一行原本写作 `1/10`（10 拍），其中 2 个位置属于两幕各自的首拍，真实的尺子是 8。
**数没算错，尺子不对**：改成对数以后，分子的那个 1（`system-lidar/step-2`）才和
分母里的每一处位置是同一件事。这个数现在由 `tools/player_smoke.mjs` 自己打印
（见下），不再是一次性脚本里的东西。

**这张表推翻了「把改善归功于新提示词」这个顺理成章的说法。** 抛体那 14 个静拍是**布局与绘制层**
（`_flight` 把抛物线挂到球身上、`length_scale` 让 `magnitude` 生效）修好的——
**旧 storyboard 走一遍新布局就已经从 14 降到 0**。R1 对「会不会动」的直接贡献很小；
它的功绩在 ②③ 两节：单位对了、状态多了 6 倍、纯文字节拍没了。

（`obstacle` 的「旧+新布局」一列是 1/8，两列都是同一拍 `system-lidar/step-2`——
**新布局没有改善它**，因为那一拍的问题不是几何，见下。）

**修正一处旧数字**：上一节表格里的「相邻两拍画面相同的节拍 **0/27**」是**弱口径**（含高亮）下的数字。
同一个工具在 `m6-motion` 的四份产物上跑是 0/33；换强口径是 **1/33**。0/27 本身没错，
但它比读起来要弱——**这里改成强口径，因为这一轮的命题是「画面真的变了吗」，不是「有没有东西亮了一下」。**

**这把尺子现在长在工具里了**（`tools/player_smoke.mjs`）。它原来只有弱口径的硬失败
（逐调用完全相同才 `exit 1`），强口径只存在于一次性脚本里，等于「量过」但没留下量具。
现在它两种都算：弱口径照旧硬失败，强口径**每幕列出**几何未变的那几拍并点名，末尾给一个总数。

**强口径不设硬失败是有意的，不是漏了。** 契约明文允许「只高亮一个对象」的节拍
（`StoryboardStep._must_change_something` 是「高亮**或**状态」），避障文档的《系统组成》就是
「先点亮整个系统、再点亮雷达」，那一拍**本就不该动**——一个比契约更严的冒烟检查会否掉合法产物。
这一轮要治的是「整幕都是它」，那是教学设计的判断，不是机制缺陷，所以**量出来、点出名**，
把判断留给人和提示词。

### ⑤ 顺带查出来的两个洞（都已记录，未修）

**`readout.align` 被声明为「可被节拍改变」，但没有任何代码在播放期读它。**
`layout.py:1071` 的 `_align_of(obj)` 在**布局期**读 `obj.props["align"]` 并烘焙进元素，
布局只跑一次——所以它是个合法的**静态**属性，却不该出现在 `live_props` 里。
后果：模型往某一拍写 `{hud: {align: "left"}}`，`_check_prop` 放行、**`step_state_inert` 也放行**，
校验台承诺画面会变，而什么都不变。

这正是 `step_state_inert` 存在的理由，却坐在校验台自己信任的那张表里。
漂移测试也抓不到：`registry.js` 与 `registry.py` **两边声明一致、一起错**（`34 passed`）——
它保证的是「两边不漂移」，不是「声明为真」。修法就是 `axis.origin` 的先例（`registry.py:205` 的注释
「`origin` 不在这里：没有绘制函数读它」）。

**已修（2026-09-15）**：`align` 从 `live_props` 移出、留在 `props` 里，`registry.js` 的镜像同步，
校验台加了一对测试（写进 `object_states` 被拒 / 写在对象上放行）。

查的时候翻出更深的一层，**这一层才是根**：`drawReadout` 连**烘焙好的** `element.align` 都没读过，
它把 `ctx.textAlign` 硬编码成 `"left"`。所以 `align` 不是「只有播放期读不到」，
而是**从头到尾没有任何读者**——`layout.py` 算它、`ReadoutElement` 带着它、绘制函数无视它。
只把它从 `live_props` 挪进 `props`，等于把谎话从一组搬到另一组，所以两半一起修：
绘制函数改读元素上烘焙的那个值（**不是** `view.lookup`——那会把它变回 live 属性，
让面板在节拍之间左右横跳）。**现有产物无一受影响**：手写 ROS 样本写的就是 `"left"`，
其余全走 `_align_of` 的默认值，18 份产物的绘制调用逐字节不变。

**`hub` 预设的第二拍两轮都静止**——换强口径以后能说清它到底是什么了。
`m5` 与 `m6` 都停在 `system-lidar/step-2`，`r2` 换了个 scene id（`scene-1/step-2`）停在**同一个位置**。
三份产物、两次运行、两个不同的 storyboard，同一拍不动——这不是模型偶发，是 `hub` 的槽位或
那一步的写法有结构问题。它的性质也定了：这一拍**不是完全没动，是只换了高亮**，
而且是 `r2-*` 三份产物里**唯一**一处强口径静拍（1/38）。旧产物里同类的有 **31 处 /164**——
**R1 基本清掉了「靠高亮凑一拍」这个写法，只剩 `hub` 这一处结构性的。未修。**

## 速度：一次十几分钟的生成，是怎么变成 51 秒的（2026-09-16）

前端页面的第一次真人验收，结论是一句话：**「跑了十多分钟都没出来，这个速度是绝对不行的。」**
查完之后，问题不在链路代码里，在一个环境变量里。

### 先看时间花在哪（时间戳，不是猜测）

`data/generated/` 的文件时间戳把那次运行完整记了下来：

| 时刻 | 发生了什么 |
|---|---|
| 21:38:50 | `lesson-*.json` 落盘——课程那一步结束 |
| 21:47:30 | 分镜第 1 次返回（**520 秒**），被驳回 |
| 21:51:07 | 分镜第 2 次返回（**217 秒**），成功 |

分镜一步就是 **737 秒**，其中 **520 秒完全白烧**。

### 三个叠加的原因

**① `deepseek-v4-pro` 是推理模型。** 拿**同一个分镜 prompt** 在两个模型上各跑一次：

| | `deepseek-v4-pro` | `deepseek-flash` |
|---|---|---|
| 墙钟 | **461.2 s** | **48.3 s** |
| completion tokens | 28,917 | 11,814 |
| 其中推理 | **26,113** | 8,561 |
| 正文 | 9,083 字符 | **10,310 字符** |
| JSON | 可解析 | 可解析 |

v4-pro 把 2.6 万个 token 花在看不见的推理上，总输出 **28,917 / 上限 32,768**——
**紧贴天花板**，所以会时灵时不灵地被截断。flash 快 9.5 倍，正文反而更长。

**② 截断被误诊成 JSON 语法错。** 第 1 次的原始输出停在半句话上：

```
          "label": "控制循环",
          "props": { "text":
```

而 `LLMClient.chat` 当时**只在正文为空时**才看 `finish_reason`——那个检查写在
`if not content.strip():` 分支**里面**。正文非空但被截断时，它一路走到 `json.loads`，
报出 `Expecting ',' delimiter: line 234 column 10`。

**③ 于是重试用同一个预算、同一句话，全价重跑。** 这就是那 520 秒。
prompt 里对模型说的是「上一次输出校验失败：Expecting ',' delimiter」——
**它指向标点，而问题在长度。**

### 改了什么

| 改动 | 文件 |
|---|---|
| 模型换 `deepseek-flash` | `.env`（本地）与 `.env.example`（已提交） |
| 新增 `LLMTruncatedError(ValueError)`，正文非空也认得出截断 | `llm.py` |
| 新增 `retry_suffix(exc)`，截断时说「请精简」而不是「改标点」 | `llm.py` |
| 两个 agent 改用它 | `knowledge/agent.py`、`storyboard/agent.py` |
| 页面文案：删掉已经失真的「避障那份跑了将近 8 分钟」 | `frontend/web/index.html` |

`LLMTruncatedError` **故意是 `ValueError`**（和 `LLMBudgetExhaustedError` 恰好相反）：
预算被推理吃光，再问一次还是吃光；但截断**是有出路的**——下一次写短一点就装得下。
所以它必须留在 agent 的 `except ValueError` 重试环里，而不是逃出去。

### 这次**没有**解决的问题：`key_point_missing`

抛体那份（20 个 block，至少 6 幕）换成 flash 之后跑了 **290.7 秒仍然失败**，
卡在「课程要点要逐字抄进节拍」这条规则上。第 2、3 次重试的驳回理由**大小完全一样**
（都是 202 字节），说明重试反馈对这条规则不起作用。
**这是校验规则严格度的问题，和换哪个模型无关**，单独记在这里。

另外，**没有**拿 v4-pro 跑过抛体那份，所以**不能据此说 flash 质量更差**。

### 顺带发现：`config/app.example.yaml` 里的 `llm:` 块是死的

```yaml

  base_url: https://api.deepseek.com
  model: deepseek-v4-pro
```

**没有任何代码读这一块。** `load_llm_config()` 只认环境变量
（`DEEPSEEK_BASE` / `DEEPSEEK_KEY` / `DEEPSEEK_MODEL`），`config.py` 里
`KnowledgeSettings` / `AnimationSettings` / `StoryboardSettings` 三个模型没有一个碰它。
**改了 YAML 毫无反应的原因就在这里。记录，未修。**

这一幕整拍的教学内容就是「这四部分分别是什么」，现在画面说得出这句话了。
`after-body-labels-lane.png` 是第二幕（`lane`）第 5 拍，用新的 `?scene=1&step=4` 截的。

**顺带改掉一句写在注释里的错话。** `annotation()` 上面原来写着：绘制函数自己画文字，
是因为「一个没有数字的 `dimension` 不成其为 dimension——**不像 `body` 的名字，
那只是关于对象的说明，而不是它几何的一部分**」。这半句是反的：
**正因为是说明，才更该画出来**，而 `drawVector` / `drawAxis` / `drawDimension` / `drawAngle`
本来就都画自己的标签。`body` 是唯一一个不画的场景对象。

**这件事没有廉价通用网，我把原因写进测试了。** 最自然的推广是「绘制函数必须把
storyboard 填进去的每个字段都呈现出来」——**它抓不到这一处**：`element.label` 在
`primitives.js` 里**确实被读了**，被那四个绘制函数读的，任何文件级检查都会通过。
遗漏是**逐图元**的，落在唯一跳过它的那个绘制函数上，而模型里推不出
「`body` 和 `axis` 在这个问题上有什么不同」。所以老实的做法是一个**具名检查**而不是一条规则——
测试里那段 docstring 就是写这件事的，免得下次有人把它当网用。

### A4：`axis.range` —— 从「一句注释」变成一条门禁

`drawAxis` 上面本来就写着这件事：「没有 `range`，坐标轴就是一根带刻痕的箭头，
抛体那份文档画了两根那样的东西还管它们叫坐标轴」。**写得很对，然后那两处照画不误**——
因为**注释不是门禁**。

做法沿用 `required_relations` 的形状，加上它的下一层问题：

| | 问的是 | 缺了会怎样 |
|---|---|---|
| `required_relations` | 布局能不能算出它画在哪 | 画面**缺一块**，会报错 |
| `required_props` | 画出来的**还是不是它该有的样子** | 画面**完整且没有意义**，不报错 |

`axis.required_props = ("range",)`，校验台出 `required_prop_missing`，词表那一行也把
「**必须填写**」说出来（不说的话，模型是在猜一条没告诉过它的规则——D5 记的同一个失败）。

**门禁第一次遇到真输出就有话说**：拿今天的校验台审 `r2-projectile_motion` 的 storyboard，
不多不少两处，正好是那两根轴。

> 这也意味着 `r2-*` 那三份产物**按今天的规则是不合格的**（抛体两处 `required_prop_missing`）。
> **没有重跑**——重跑要花 LLM 调用，而这一处分歧是已知且已定位的。

### 小事：`?scene=N&step=N`

播放器原来只认 `?spec=`。无头截图只能拍「按下快门那一刻屏幕上的东西」，
所以在那之前**任何人能看两眼的画面只有第一幕第一拍**——
「四个一模一样的盒子」记进文档、另外两份没细看，就是这么来的。
现在越界会被 clamp 而不是报错（URL 里写错个数应该给你一张图，不是白屏）。

### 边界

- **没有重跑真链路。** 这轮改的是绘制层与校验台，`r2-*` 产物是旧的。
- **交互仍然没验收。** `?scene=&step=` 解决的是「看第几拍」；
  前进/暂停/重置、拖滑杆**仍然只被离线重放过**。
- **A2（字形）已在第七轮做完**，见下一节；**A3（`readout` 排布）没做**，仍是下一轮。

## 字形库：从「声明了十个名字」到「画得出一辆车」（2026-09-15，A2 / M3-c）

A2 是四项里最大的一项，也是唯一一项需要**新建一个资产目录**的。D2 早就把字形
schema 定死了（`{d, mode, fill_rule}` + 扁平的具名 `parts`），`T2_GLYPHS` 里也一直
列着十个名字——而 `assets/glyphs/` 是空的。所以这一轮不是「让字形能画」，是
「让字形**被要**，然后画出来」。

### 一、先把声明砍到六个，其中一个是错的

十个名字里，`wheel`／`steering_wheel`／`protractor` 只是没人要——一个轮子就是原子层
已经能精确算出来的圆，而按这一轮写进 registry 的规则，**字形靠「它是一个形状」挣位置，
一个由两个数算出来的正多边形不是形状**。

真正必须删的是 `obstacle_octagon`：它的 `source` 写的是 `hand:octagon`，而 D1
在 `layout.py:162` 与 `models.py:99` 两处独立记着**相反的决定**——基线的障碍物是八顶点
在 `r` 与 `0.78r` 之间交替算出来的，是刻意参数化的。把它的数据建出来，等于用一幅手写
`d` 悄悄替掉基线那颗星。**声明和数据对不上时，先怀疑声明。**

### 二、`Path2D` 最阴的地方：三个字段错一个就静默画错

`Path2D(svgPathString)` 只带几何、不带任何样式，所以三件事必须**跟着几何一起走**：

| 字段 | 漏了会怎样 |
|---|---|
| `mode` | Tabler 是纯描边图标，用 `ctx.fill()` 画出来是**一坨实心黑块** |
| `fill_rule` | 靠子路径挖洞的图标（轮毂、散热孔）洞会被填实 |
| `parts` | 车和轮子合成一条 path，**轮子就再也动不了** |

三个字段在 schema 里都是**必填、不给默认值**，理由是同一句话：默认值会让错误静默。

### 三、`ink_box`：为什么车的第一个版本是个「徽章」

第一次截图，车画出来了，但是很小。原因是 `view_box` 是**设计网格，不是量出来的边界**：
Tabler 把车的墨迹画在 24×24 网格的 x 3..21、y 6..19 里——**三分之一的宽和五分之一的高是空的**。
把它按 `min(62/24, 40/24)` 塞进车身那个 62×40 的框，车就只有 40×40 再减掉内边距。

修法是量，不是补一个手写数字：`tools/path_bbox.py` 把 path 展平后取墨迹边界
（描边算墨迹，因为描边是骑在路径上的）。**手写一个数不行**——`--check` 会重新拉上游，
`TABLER_VERSION` 一挪，手写的数就静默过期，而症状只是「每个字形都微微不对」。

那个展平器写出来才发现一个真 bug：`"" in "Mm"` 在 Python 里是 `True`，
所以 `d` 以数字开头时会被当成隐式的 `L` 读下去，算出一个**没人写过的路径**的边界。
抓到它的是那条「以数字开头必须报错」的测试。

### 四、轮子转不起来——计划里的一条被几何证伪

原计划这一项是「轮子自转」。动手前先去看了一眼 Tabler 的车轮：

```
M15 17a2 2 0 1 0 4 0a2 2 0 1 0 -4 0     ← 一个正圆
```

**正圆绕自己的圆心旋转是恒等变换。** 代码会每帧跑、每帧算一个角度、画面上一个像素都不变——
比「字段没人读」更糟，因为它在 diff 里看起来是实现完了的。

换成 Tabler 的 `radar`：它的第 0 条路径 `M21 12h-8a1 1 0 1 0 -1 1v8a9 9 0 0 0 9 -9`
是一个 **90° 扇区**，绕两条直边相交的那个角转，变化一眼可见。于是 `lidar` 拆成
`sweep` + `outline` 两个 part——**这才是 `parts` 存在的理由第一次被兑现**。

旋转中心也是**量出来的**：取该 part 最大圆弧的圆心。雷达的扫描臂由一段 r=9 的弧画出，
圆心正是 (12,12)。这条规则在两个例子上都成立（车轮的 r=2 圆弧圆心就是轮心），
所以它是规则而不是对某一个例子的拟合——测试把车轮那一半也断言了，**尽管它不转**。

### 五、前两件事都做完了，画面上还是什么都没变

这是这一轮最该记住的一句。数据在 `assets/glyphs/`，画笔在 `glyphs.js`，
契约、校验台、播放器全部就位——**而三份真产物里模型一次都没有写 `glyph`**。

原因在词表里：它把这六个字形当成一串**光名字**打印（`- \`car\`（robotics）：…` 之前只有
`car、lidar、robot、cpu、server、package`），而 `GlyphDeclaration.note` 里
六条写好的说明**一条都没被印出来**。**这和上一轮的 `element.label` 是同一个形状**：
数据在契约里、在产物里、没人读。

修完之后每个字形带一句「它是什么、为什么这一拍该用它」，并写明判据：
**这个对象在文档里是不是一个具体的实物**——小车、雷达、服务器、数据包是；
安全距离、空旷程度、判断结论不是，那些该用 `zone`／`readout`／`dimension`。
两半都要：只说「用字形」，模型会给阈值圆圈也挂一个图标。

同一次检查还翻出两处**写错的说明**，都印在模型读的提示词里：

- `body.note` 写的是「基础形状由 glyph 选（圆/矩形/多边形/胶囊）」。**三处都不对**：
  `shape` 由角色在布局期定，根本不是可设置的 prop；而 `rect`／`circle`／`polygon`
  也不是字形名。照它写的模型会写下 `"glyph": "rect"`，被 `unknown_glyph` 打回——
  所以代价是一次重试而不是一张错图，但那句话**只可能教错**。
- `car` 的说明写着「轮子是可独立转动的 part」，而上一节刚证明那是假的。
  **模型读的说明里不该留着代码已经证伪的话。**

### 六、before / after

同一份 storyboard、同一套布局代码、同一取景（避障样例第 1 拍，`?scene=0&step=0`），
**只有字形数据在不在磁盘上有区别**——把 `GLYPH_DATA_DIR` 指向一个空目录就是 before：

| | |
|---|---|
| 改前 | `before-glyph-lane.png`——小车是一个圆角矩形 |
| 改后 | `after-glyph-lane.png`——**一辆车**，挡风线、前后轮、朝向三角都在 |

`layout._glyph_to_draw` 对没有数据的字形是**丢掉请求、退回参数化形状**，所以 before
那一格里它退化成了参数化形状。请求本身还留在 `props` 里（props 原样保留），这是它对得上的地方。

这也是为什么这对图值得留：它把「交付的到底是什么」摆在一格里——**同一个契约，
数据一到，画面自己就变了**，没有任何一处绘制代码为了这张图改过。

### 七、这一轮**没有**证明的事（重要）

**真链路至今仍然没有写过一次 `glyph`。** 上面那个 before/after 来自**手写样例**，
它本来就把 `"glyph": "car"` 写在对象上；词表那一改是否真的让模型开始要字形，
**要等下一次真链路重跑**（同样的余额限制）。所以这一轮能说的是：

- 数据、画笔、契约、校验台、播放器——**通了，并有两处独立验证**（离线重放 + 截图）；
- 词表**已经不再把字形当成一串光名字**——这是可断言的（测试按名字逐条比对说明）；
- **「模型现在会要字形了」是未验证的**，要重跑才知道。

### 八、验收是怎么做的

- **离线重放**：`node tools/player_smoke.mjs`，20 次绘制全过；相邻节拍几何无重复 `0/3`。
- **旋转 part 直接驱动**：没有一份样例会画出 `lidar` 字形（避障样例里的 `lidar` 是
  `emitter`，画的是扇面，根本不走字形绘制），所以这条**必须单独驱动**：
  同一个 body 在 t=2 与 t=4 各画一次，断言角度非零、用的是 `rotate` 而不是平移、
  而且**时间翻倍角度就翻倍**。最后一条才是关键——常数或者会漂移的累加器都能通过
  「动了没有」而破坏可复现性。把 `SPIN_TURNS_PER_SECOND` 改成 0，这条检查会带着
  正确的信息失败。
- **截图**：headless Edge 的截图**冻结在 t≈0**（不同的 `--virtual-time-budget` 出图逐字节相同），
  所以扫描臂的角度变化**不可能**靠截图对比验证——这也写在这里，免得下次有人以为它是没做。

## `readout` 面板：从「固定的 24%」到「它自己那句话有多宽」（2026-09-15，A3）

A3 是四项里的最后一项。它被记成「面板是浮在右上角的大空盒子，舞台右半常常是空的」，
动手前先量了一遍——**第二句话比第一句严重，而且不是同一个原因。**

### 一、量到的三个数

| # | 事实 | 怎么知道的 |
|---|---|---|
| 1 | **16/16 个 `readout` 都是单行**，却全都分到 230×88 的槽；其中 6 个只需要 120px 的下限 | 三份 r2 产物逐面板量 |
| 2 | **11/16 个面板，有某一拍写的文本比对象声明的更长** | 把每一拍 `states[id].text` 与对象声明的比 |
| 3 | `publisher-code` 需要 **448px**，发的框是 **230px**——**字从自己面板的右边跑了出去** | 见下面的 before 截图 |

第 2 条是这一轮真正要修的东西。`text` 是 live prop，而面板是在**任何节拍跑之前**定好大小的：

```
param_panel   声明「四个关键参数」(6 字)
              beat 7 写「雷达有效半径2到8米；控制循环80ms」(20 字)

decision_readout  声明「比较最近障碍物距离与安全距离」
                  beat 4 写「比较左右可通行空间并选择更空旷一侧转向」
```

`fillText` 不看盒子，所以字照写不误，**没有任何一层说话**。这和项目此前抓到的每一处
是同一个形状：一个没人读的量，和一个看不出问题的画面。

### 二、面板：宽高都从文本算，而且装的是**所有节拍会写的**文本

度量从 `drawReadout` 搬进 `layout.py`。搬家的理由不是「谁更该算」，是
**那条规则从来没跑过**：`drawReadout` 一直有「宽度缺省时按文本拟合」的分支，
而 `layout` 永远会设 `element.width`，把它整个盖掉。盒子是几何，几何是这一层的活（D3），
而 `_check_fit` 只查得到这一层自己定的盒子。

三条判断写在代码里，都值得在这里说一遍：

- **按所有节拍会写的文本定尺寸，不是按声明的那句。** 11/16 就是这么漏出去的。
- **宽高各自取最大，不假设最宽的那句也是最高的那句。** 一拍把面板改写成两行短句，
  句子变窄变高——只取其一，另一个方向照样溢出。
- **没有比例了。** 面板要多宽就多宽，上限是画布装得下的宽度；一行装不下的句子
  **报错**而不是写到画布外面。原来那个 24% 的「上限」正是让溢出变成静默的东西，
  换一个新的比例只是把悬崖挪个地方。

`MIN_PANEL_WIDTH` 保留（两字标题也要有个盒子），`PANEL_WIDTH_RATIO`、
`PANEL_HEIGHT`、`MIN_PANEL_HEIGHT` 和 `_panel_height` 一起退场。

**`_panel_height` 的退场方式值得单独说。** 它做的是「按 N 块把每块缩小到塞得进这一列」。
那会产生**文本装不下的盒子**，于是绘制端把它重新撑大，两块面板就画到了一起——
而 `_check_fit` 查的是它刚算出来、并且认为没问题的那两个矩形。**今天没炸，纯属 16/16 恰好单行。**
现在面板按文本定尺寸，让位的是**列本身**：从 `PANEL_TOP_RATIO` 起，需要时往外撑到边距，
真装不下才是失败。

### 三、预设：面板占的是**一个角**，不是**一条列**

`FIELD_RIGHT_RATIO = 0.60`、`CHAIN_RIGHT_RATIO = 0.84`、`HUB_RADIUS_X_RATIO = 0.22`——
三个常量都是**为了躲开 readout 列**才取的，而且**都是按最坏情况取的**：
一个带一句说明的 `field` 场景，一直在按七块面板的墙给自己让位。

所以 `_Frame` 回答的不是「右边到哪」，是**「在你这个高度上，右边还能到哪」**：
和面板齐平的地方是面板的左边缘，面板上面、下面、两块之间就是舞台边距。
被接到 `_Frame` 的是 `chain` / `field` / `hub`；另外两个不接，各有理由：

- **`lane` 不接，而且是唯一一个不该接的。** 它的障碍物坐标被
  `test_the_lane_ratios_are_the_baselines_own_proportions` 锁死在
  `templates.py` 自己的分数上（M2 的验收就是靠它）。为了填满画面去挪障碍物，
  等于把那个对照基准废掉，换来的是一幕本来就只有四个对象的画面。
- **`generic` 不接。** 它是一列有序的对象，没有横向结构可以撑开。

**面板只会变窄或不变，又贴了右边，所以 `_Frame` 给出来的可用宽度相对今天是只增不减的。**

### 四、顺手抓到的四处，三处是我自己写出来的

1. **`hub` 的注释把约束归错了。** 原话是「x 半径取 0.22 是因为 0.30 时最右边的叶子会撞上
   面板列」。扫一遍常量就知道：0.29 挂在 **`target`，左边那片叶子，画到画布左边缘外面**，
   **面板根本没出现在失败信息里**——四叶 hub 的角度是 -90°/0°/90°/180°，
   右上角没有叶子可以撞。这个数是左边距定的，注释却说是面板定的，两者只是碰巧接近。
2. **`chain` 用节点的高的一半去做水平内缩。** 端节点因此跑到边距**外面**——
   还在画布上，所以什么都没失败，只是越过了布局自己刚说的那条线。改成用宽的一半。
3. **把 field 撑到边距，把轴标签顶出了画布。** 水平方向画在轴尖外 18px，
   `_check_fit` 比的是盒子，而注记没有盒子。现在 `AXIS_LABEL_GAP` 由布局预留，
   并且有一条测试把这个数和 `drawAxis` 里的那个数钉在一起。
4. **（不是这一轮写的）`field` 的右界该在哪个高度上问。** 第一版按「图片占据的整条带」问，
   于是每个抛体场景白让 200px——抛物线的最高点永远在射程中点，右边缘只在**地面高度**上碰到。

### S1 之后新发现的两处质量缺口（发现时校验台查不出，2026-09-13 两条均已修）

**① `generic` 兜底吸附——5 个场景里 3 个「更具体的预设本来可用却没选」。**
`tools/check_storyboard.py` 的逐场景报告：

```
scene-1: 选了 `generic`；可用 ['field', 'generic']   ← field 本来可用
scene-2: 选了 `generic`；可用 ['field', 'generic']   ← field 本来可用
scene-3: 选了 `generic`；可用 ['field', 'generic']   ← field 本来可用
scene-4: 选了 `generic`；可用 ['generic']            ← 真的只能 generic
scene-5: 选了 `generic`；可用 ['generic']            ← 真的只能 generic
```

真因在词表的措辞：`generic` 被写成「**永远合法的兜底预设**」。模型在优化「别被打回」，
兜底于是成了最优解。**这不是能力不足，是激励方向错了。**
校验台完全看不出这个差别——两个预设都是合法值——**但画面看得出来**：`field` 有坐标轴与轨迹槽位，
`generic` 只有竖排对象加说明面板。修法方向：词表里不要再把它描述成「兜底」，
并在 prompt 里明说「能用具体预设时必须用」。

**② 该有的关系没写——布局层画不出来。**
`unresolved_ref` 只校验**写出来的**引用能不能解析，**从不校验该有的关系有没有写**。实测漏网：

| 对象 | 角色 | 缺的关系 | 后果 |
|---|---|---|---|
| `gravity_vector` | force | `of`／`component_of` | 重力作用在**谁**身上？ |
| `range_dimension` | range | `from`／`to` | 量的是**哪两点之间**？ |
| `height_dimension` | height | 同上 | 同上 |
| `ideal_trajectory`／`real_trajectory` | trajectory | `of` | 从**哪个**物体画出来？ |

这些**全部通过校验台**，然后在布局层无解——没有 `from`／`to` 就没法在「两个不存在的东西」之间
画标注线。**这是 M2 的前置，不是 M2 的内容。**
判据已经由 `tools/check_storyboard.py` 的 `_unanchored` 给出：它从 registry 的
`Primitive.relations` 推，不手抄表，所以不会与布局能力漂移。

**③ 控件为 0 的四个场景——判为不是缺陷。** `no_interactive_demo` 要求整份分镜**至少一个**
场景有控件，模型照做了（只有 scene-3 有可调量）。在「定义／分类／注意事项」这类场景硬塞控件，
产出的正是那条规则要禁的**空旋钮**。检查是对的，不改。

**这三条都不阻塞 M1**——M1 的输入是手写的基线 sample，不是这份抛体输出。
① 与 ② 是 **M2 的前置**，在做布局层之前解决。**两条已于 2026-09-13 修完，验证如下。**

**① `generic` 吸附——修法。** `Preset.note` 不再自称「永远合法的兜底」，改成「只在没有任何
更具体的预设可用时才选它」；词表里预设**按具体程度排序**（必需角色多的在前、`generic` 排最后），
并写明「能用更具体的预设就必须用」。
措辞没法断言，排序可以——`test_the_fallback_preset_is_offered_last` 看住这个顺序。

**② 必需关系——修法。** `Primitive` 新增 `required_relations`，判据只有一个问题：
**布局层没有它就无处安放。** `dimension` 没有 `from`/`to` 就不知道量的是哪两点，
`trace` 没有 `of` 就不知道是谁的轨迹，`vector` 没有 `of` 就推不动任何东西——
这些都不是「画得松」，是**没有几何**，而 `StoryboardIR` 没有坐标可以退（D3）。
校验台新增 `required_relation_missing`。

**回放 S1 那份真产物：从 0 处问题变成 7 处**，与上面那张表的每一条都对上，
并多出 2 处当时没看到的——`v0x_vector` / `v0y_vector` 也缺 `of`：速度分解出来的分量
同样得说清作用在谁身上，而旧的弱规则（「声明了关系但一个都没设」）看不出这个差别。
**这条把「画面缺一块但报成功」变成了响亮的失败**，这正是它作为 M2 前置的意义。

`component_of` 与 `between` **故意保持可选**：前者只用于分解出来的分量，后者只用于被测量的角。
设成必填会把最常见的那种写法（整条速度矢量、没标角度的场景）误伤掉。
`test_the_optional_relations_stay_optional` 看住这条界线。

至此 **M1 收尾、M2 前置清空**。

- **`data/samples/storyboards/*.json` 是手写的，不是模型输出。**
  它们证明的是「契约装得下基线画的东西」，**不是**「模型会写出这样的东西」。
  原计划把 S1 排在最前，正是为了避开这一点；余额归零使该理由失效，风险转为现实——
  校验台的 fixture 越干净，真实模型输出一来越容易崩。**这一步已完成**——真输出见本节 S1 结论。
- **`document_id` 是「文件路径」的哈希，不是内容哈希**（`file_parser._document_id`：
  `sha256(str(path.resolve()))`）。后果：文档改了而 `document_id` 不变，于是
  **陈旧的 LessonIR 与当前文档无法被区分**——第一次真跑撞上的正是这个（课程引用了文档里
  已经不存在的 block，而且因为 id 相同，看起来像「一致」，把排查引向了错误方向）。
  这是 `--storyboard-from` 复用旧课程时最容易踩的坑。真要修得把 id 换成内容哈希，
  但那会让所有已生成的 `lesson-*` / `storyboard-*` 文件与下游 id 失效，
  **属于需要单独决策的改动，先记录不改**。
- **装饰性对象与 `orphan_object` 有张力**：基线里的 `obstacle-2` 纯属布景、不挂任何关系，
  在新规则下会被判「画了但没教」。样例把两个障碍物都放进最后一拍高亮（语义上也对：
  比较左右空旷度本来就是同时在说这两个障碍物）。但如果以后有大量纯布景对象，这条规则要重新讨论。

- **`data/samples/projectile_motion.md` 有未提交改动**（用户手动加了「（以斜抛运动为例）」）。
  任何提交都**不得** `git add -A` 把它卷进来或还原掉。
- **`frontend/demo/app.js` 必须保持不可达**。不要顺手修好 `index.html` 的注释——那是对照物，
  也是 Standing Correction 明确要保的东西。
- **手写 fixture 的写实性风险**：校验台的 fixture 若太干净，真实模型输出一来就会崩。
